# J5 실물 디버깅 — 2026-09-09

## 확인된 현상과 수정

Windows 자체의 실행 오류가 아니라, J5 관측 원의 중심·반지름 품질 검사에서
측정이 거부되어 Full Auto가 다음 관절로 진행하지 못한 상황이다.

확인된 코드 결함은 두 가지다.

1. `start_full_auto()`는 상태 조회 타이머를 멈추지만 영상 타이머는 유지한다.
   `update_video_frame()`은 직접 `capture_image()`를 호출한 뒤
   `get_marker_transform()`으로 다시 프레임을 취득한다. 동시에 수집 워커도
   같은 RealSense 파이프라인과 마커 검출기를 사용하므로 프레임을 나눠 소비하고
   검출 상태에 동시에 접근할 수 있다.
2. `compute_calibration_results()`가 원 일치 검사에서 예외를 처리하면서 이미
   계산된 진단값을 버려 `[SWEEP QUALITY] {}`만 남겼다.

수정 후 실행 중인 `active_worker`가 있을 때 GUI는 카메라의 최신 이미지만
표시하고, 자체 취득·마커 검출을 수행하지 않는다. 수동 티칭 대화상자에서
워커가 기다리는 동안과 워커 종료 후에는 GUI 취득을 허용한다. 워커가
이동만 하고 아직 프레임을 취득하지 않는 구간에는 마지막 영상과
`Waiting for next camera frame` 안내가 표시된다.
거부된 J3/J5 측정에는 상대 보정각, 중심·반지름 차이, 프레임 수, 원호 범위와
계산된 RMS가 남는다. 거부 결과를 보정값으로 승격하지 않는다.

각도 0.06°와 원 일치 0.5 mm 기준, 수렴·저장·롤백 정책은 변경하지 않았다.
별도의 자동 재시도나 스윕 범위 확대도 추가하지 않았다.

## 기존 원본의 오프라인 재현

입력: `result/result_txt/sweep_points_right_joint_{A,B,C}_axis_{4,6,5}.txt`.
각 파일에 5개 블록이 있으며 기존 로그의 두 패스와 일치한다.

| 패스/반복 | 상대 보정각 ° | 중심 차이 mm | 반지름 차이 mm | 판정 |
|---|---:|---:|---:|---|
| 1/1 | -0.26200 | 1.68278 | 1.07374 | 측정 수락, 미수렴 |
| 1/2 | +0.02324 | 0.96759 | 0.86594 | 기하 품질 거부 |
| 2/1 | -0.21765 | 2.44599 | 2.05238 | 측정 수락, 미수렴 |
| 2/2 | -0.08456 | 0.40153 | 0.04253 | 측정 수락, 미수렴 |
| 2/3 | -0.02961 | 1.62104 | 1.52566 | 기하 품질 거부 |

마지막 원호는 약 28~29°이고 독립 원 피팅의 곡률 높이는 약 1.75~1.81 mm다.
따라서 약 0.11 mm의 점 잔차가 원 중심까지 같은 정확도로 결정한다는 뜻은 아니다.
마지막 블록의 순서를 보존한 40회 프레임 재표본화에서 중심 차이의
2.5~97.5 백분위는 0.231~2.669 mm였다. 이는 표본 선택에 대한 민감도이며,
실제 기계 오차의 신뢰구간은 아니다. 시간 상관과 체계적 PnP 오차를 제거하지 않는다.

재현 명령:

```powershell
.\.venv\Scripts\python.exe -X utf8 scratch/analyze_j5_capture.py
```

출력: `result/j5_capture_analysis.json`.

## 현장 감시하의 실물 반복 측정

- 연결: `192.168.1.40:50051`, SDK 정보 `A@v1.2`.
- 카메라: 실제 D405, 1280×720 @ 30 fps. 고정 `camera_intrinsics.yaml` 사용.
- 사용자 현장 감시 및 비상정지 준비 확인 후 3회 수행.
- J5 명령은 **-0.30234375°**에 고정. 기존 오른팔 자세에서 J4/J6 ±15°,
  J5 -15~0° 상대 범위, 각 스윕 15초. 다른 관절 목표 변경 없음.
- 홈오프셋 기록, 전원/서보/제어모드 변경 없음. 종료 시 모든 config 파일의
  SHA-256이 시작 시점과 동일함을 확인했다.

| 반복 | 상대 보정각 ° | 중심 차이 mm | 반지름 차이 mm | A/B/C 프레임 수 | 판정 |
|---|---:|---:|---:|---|---|
| 1 | +0.00140 | 0.60451 | 0.58278 | 451/457/461 | 기하 품질 거부 |
| 2 | +0.01782 | 0.39696 | 0.39974 | 461/453/461 | 기존 각도·기하 기준 만족 |
| 3 | +0.01345 | 0.22919 | 0.21563 | 461/453/462 | 기존 각도·기하 기준 만족 |

원본과 측정 로그: `result/j5_repeat_20260909_162129/`.
이 검사는 고정 명령에서 측정기만 호출했다. 결과의 `converged=False`는
반복 수렴 제어기를 호출하지 않았기 때문이다. Full Auto 성공이나 결과 적용으로
보고하지 않는다.

동일 명령에서도 판정이 달라지는 반복성이 확인됐다. 기존 GUI 기록의
약 250프레임 대비 단독 수집에서는 약 450프레임을 확보했다.
GUI 중복 취득은 확인된 결함이며 표본 감소에 기여할 수 있다. 다만 카메라
재초기화, 노출, 실행 시점도 달라졌으므로 원 중심 차이 전체를 이 결함 하나로
설명하거나 실제 축 오차·PnP 편향이 전혀 없다고 단정하지 않는다.

## 검증

- 새 진단 테스트: 수정 전 빈 진단으로 실패, 수정 후 통과.
- GUI 재현 테스트: 수정 전 영상·상태 조회가 워커 프레임을 소비하여 2개 실패,
  수정 후 4개 통과. 대기/티칭 중 GUI 취득, 캐시 영상 표시,
  프레임 만료 시 마지막 영상 유지와 대기 안내도 확인.
- 실제 D405 + Qt 타이머 + QThread, 로봇 연결 없는 정지 영상 검사:
  6초 동안 GUI 취득 **0회**, 워커 취득 **173회**, 1280×720 영상 표시 성공.
  워커 종료 후 GUI 취득 2회로 정상 복귀.
- 전체 단위·회귀 검사: **161개, 실패 0, 오류 0, 생략 2** (159개 통과).
  생략된 것은 로컬 M 모델 시뮬레이터를 요구하는 opt-in SDK 연결 검사다.
  이 실물 A 모델을 해당 검사 대신 사용하지 않았다.
- Windows 기본 문자 인코딩에 의존하는 기존 테스트 때문에 UTF-8 모드 사용.
  기존 기구학 테스트는 로컬에 있는 공식 SDK 모델 URDF 경로를 지정했다.

```powershell
$env:RBY1_MODEL_DIR='C:/Users/User/Desktop/RBY1_utils/robot_utils/models/rby1m/urdf'
$env:PYTHONUTF8='1'
.\.venv\Scripts\python.exe -m unittest discover -s tests -p 'test_*.py' -q
```

로그: `result/j5_regression_tests_final.log`.

**검증 범위의 한계:** 수정된 GUI로 양팔 Full Auto 전 과정을 다시 실행하지는
않았다. 재시작 후에도 원 일치 검사가 반복 실패하면 원본을 추가 확보하여
영상 잡음·표본 수·노출·원호 범위·기구 반복성을 비교해야 한다. 품질 문턱을
느슨하게 만들어 결과를 적용하는 것으로 대체하지 않는다.
