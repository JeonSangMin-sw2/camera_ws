# 작업 흐름과 도입 절차

## 계획과 승인
- 구현 전에 **목표 / 범위 / 완료 조건 / 검증 방법**을 먼저 제시하고(`CLAUDE.md` 4의 단계별 계획 형식), 사용자의 '진행' 지시 후 착수한다. `[wbm]`
- 새 기능은 **detail 요구(R) → detail 기능(F)·report 명칭 사전 → 코드** 순서로 맞춘다. 근거 요구가 없는 기능, 명칭 사전에 없는 이름은 만들기 전에 사용자와 먼저 정한다.
- 요구사항은 MECE(중복 없음·누락 없음)로 나누고, 누락 후보를 발견하면 사용자에게 알린다.
- 선택지를 제시했다면 사용자가 고른 것만 적용한다. 채택·미채택 이유는 결과 보고에 포함한다. `[cam]`
- 사용자 요구가 기존 규칙을 바꾸는 경우, 무엇이 무엇으로 바뀌는지 명시한다. `[wbm]`

## 새 기술·라이브러리 도입 절차
1. 공식 문서에서 개념과 요구사항, **호환 릴리스 버전**을 확인한다. 최신 문서의 명령을 현재 환경에 그대로 섞지 않는다. `[isaac]`
2. 최소 예제를 먼저 실행한다 (공식 예제를 따라가는 단계와 우리 환경의 최소 구성으로 재설계하는 단계를 구분).
3. 동일 목적의 기존 방식과 **같은 조건으로** 비교한다. 대표성 없는 벤치마크로 가치를 판단하지 않는다.
4. 더 쉬운 대안을 검토한다: 바이너리로 충분하면 소스 빌드 회피, 병목 하나만 교체, 기존 구현 유지도 정상적인 결론.
5. 판단을 **유지 / 보류 / 제외** 중 하나로 보고한다.

## 멈춰야 할 때
무한 반복과 폭주를 막기 위해, 한도에 닿으면 멈추고 **시도한 것 / 결과 / 남은 가설**을 보고한 뒤 사용자 판단을 받습니다. 같은 문제를 3번 고쳤는데도 실패하는 것, 같은 에러가 2번 반복되는 것, 같은 명령을 고친 것 없이 다시 실행하는 것은 hook이 멈춥니다. 아래 둘은 hook이 판정할 수 없으므로 AI가 스스로 판단합니다.
- 해결하려면 기준 완화, 실기 동작, 규칙 변경이 필요해 보임
- 원인을 모르는 채로 수정 범위가 계속 커짐
