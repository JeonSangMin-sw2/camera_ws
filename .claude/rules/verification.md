# 검증 수준과 디버깅

## 검증 수준 표기
결과 보고와 아카이브 process 진행 기록에서 모두 같은 표기를 씁니다.

| 표기 | 의미 |
|---|---|
| ❌ 미검증 | 실행하지 않음 |
| ⚪ 코드 분석만 | G1 또는 코드 검토만 수행 |
| 🟠 오프라인 테스트 | G2~G4까지 통과. 시뮬레이터·합성 입력·재생 데이터로 한 것까지 포함하고, 실기는 미검증 |
| 🟢 실기 검증 완료 | G5까지 통과. 실제 장비·사용자 환경에서 합격 기준 충족 |

## 검증 경계 명시
- 모든 검증 결과에는 **이번 결과가 의미하지 않는 것**을 함께 적는다. 예: "합성 목표 검증이며 사람 연속 추종 합격은 아니다." `[wbm]`
- 오프라인 테스트(시뮬레이터 포함) 통과는 실기 통과가 아니다. `[cam]` `[wbm]`
- 확인된 원인과 추정 원인을 구분한다. 인과가 확정되지 않았으면 그렇다고 쓴다. `[wbm]`
- 성과를 부풀리지 않는다. 달성하지 못한 목표는 "…를 주장하지 않는다"로 명시한다. `[wbm]`
- 단일 증거로 결론 내지 않는다. 여러 신호를 교차 확인한다. `[rby1]`

## 디버깅
- GUI 출력만 보고 판단하지 말고 로그 파일을 본다. 사용자가 일부만 보여주면 필요한 파일을 요청한다. `[cam]`
- 한 번에 여러 수정을 넣었는데 상황이 악화되면, 그 수정분을 모두 되돌리고 하나씩 다시 진행한다 (되돌리기는 ask 권한이다). `[cam]`
- 약한 방향이 여러 개면 동시에 검증한다. 하나를 고치면 남은 오차가 다른 방향으로 쏠릴 수 있다. `[cam]`
- 가용성을 한 라이브러리만으로 판단하지 않는다 (예: torch가 GPU를 본다고 다른 경로도 된다는 보장 없음). `[isaac]`
- 프로세스 정리는 프로세스 그룹 단위로 하고, 확인용 grep이 자기 자신에 매칭되지 않게 한다. `[isaac]`
